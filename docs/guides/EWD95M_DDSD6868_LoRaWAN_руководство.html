Опрос DDSD6868 через Ebyte EWD95M по LoRaWAN

Счётчик CHZSJ DDSD6868 → RS-485 (Modbus RTU) → контроллер опроса → DTU Ebyte EWD95M → радио RU864 → базовая станция Вега БС-1.2 → сетевой сервер → JSON.

Два условия, без которых ничего не заработает 1. Модем должен работать в плане RU864. Проверено: EWD95M его поддерживает, регион переключён с EU868 на RU864 и сохранён.
2. Карта регистров DDSD6868 у производителя 浙江虹吉电气 не опубликована в стандартном виде, в сети встречаются разные варианты. Адреса ниже — типовые для этой серии, их нужно подтвердить по паспорту или проверкой из раздела «Как убедиться».

Перед началом

  • Счётчик запитан: фаза в клемму 1, ноль в клемму 3, дисплей показывает ~220 В.
  • RS-485 счётчика: клемма 6 = A, клемма 5 = B. Импульсный выход (1 = P+, 2 = P−) не используем.
  • Под рукой USB-RS485 адаптер (COM5) — им проверяем счётчик до того, как трогать модем.
  • Известны DevEUI / JoinEUI / AppKey модема (наклейка, паспорт или чтение через AT).
  • БС-1.2 в сети и видна в сетевом сервере (ChirpStack или IOT Vega Server) с планом RU864.

Регистр общей активной энергии

Наиболее распространённая карта для однофазных DDSD/DDS с Modbus (вариант A) и альтернативная (вариант B), встречающаяся у той же серии:

ПараметрВариант AВариант BФормат

Напряжение, В0x00080x0200uint16 × 0.1
Ток, А0x00090x0201uint16 × 0.01 (или ×0.001)
Активная мощность, Вт0x000A0x0202uint16 / uint32
Частота, Гц0x000C0x0205uint16 × 0.01

Структура запроса (функция 03 «Read Holding Registers», адрес 1, регистр 0x0000, 2 регистра):

01адрес счётчика
03функция
00 00старт. регистр
00 02кол-во регистров
C4 0BCRC16 (lo, hi)
Запрос:            01 03 00 00 00 02 C4 0B
Ответ (uint32):    01 03 04 00 01 E2 40 E2 A3   → 0x0001E240 = 123456 → ×0.01 = 1234.56 кВт·ч
Ответ (float32):   01 03 04 44 9A 51 EC F2 F1   → IEEE754 BE = 1234.56 кВт·ч

Если счётчик отвечает исключением 01 83 02 ..., регистра нет — переходи к варианту B. Если молчит на 03, попробуй функцию 04 (Input Registers): часть прошивок отдаёт измерения только через неё.

Как убедиться, не гадая Подключи клеммы 6 → A и 5 → B адаптера COM5 и запусти Счетчик\ddsd6868_scan.py. Скрипт перебирает скорости, адреса и функции, затем читает регистры 0x0000–0x00FF и печатает каждое слово как uint16 / uint32 / float32. Ищи в выводе число, совпадающее с дисплеем: ~2200 (напряжение ×0.1), 5000 (частота ×0.01) и показание энергии. Так адрес и формат регистра энергии становятся фактом, а не предположением. Если Modbus молчит совсем, скрипт пробует DL/T645 и выводит адрес счётчика.

Кто опрашивает счётчик: что умеет и чего не умеет EWD95M

Проверено на самом модуле Прошивка EWD95M (STM32 LoRaMac AT-набор Ebyte, команды с префиксом AT+C…) не содержит ни режима Modbus-мастера, ни таймера автоопроса, ни списка команд. Модем умеет отправить в эфир то, что ему дали командой AT+SEND, и принять downlink. Значит, запрос к счётчику должен формировать кто-то ещё.

Два рабочих варианта, оба с тем же декодером из шага 3:

ВариантКак работаетПлюсы / минусы
A. Контроллер между счётчиком и модемом (рекомендуется)ESP32 (или любой MCU) по RS-485 раз в час шлёт счётчику Modbus-запрос, получает ответ и отдаёт его модему через UART командой AT+SEND=2:1:0:<hex ответа>. Модем в классе A, спит между отправками.Надёжно, автономно, интервал любой. Нужен один ESP32 с MAX485 (такой уже читает печной счётчик). Модем и ESP32 связаны по UART (TTL) или RS-485.
B. Опрос из сервера через downlinkМодем в классе C, к RS-485 подключён только счётчик. Сервер по расписанию шлёт downlink с Modbus-запросом, модем выводит его в RS-485, ответ счётчика уходит uplink'ом.Без дополнительного железа, но требует класса C (модем всегда слушает эфир, питание от сети) и проверки, что прошивка выводит принятый downlink в порт «как есть», а не как текст +RECV:…. На столе это не подтверждено.

Порт модема для обоих вариантов: AT+UART=? вернул 2:0, то есть 9600 бод без чётности. Счётчик по Modbus тоже 9600 8N1, поэтому в варианте B скорости совпадают. В варианте A ESP32 общается со счётчиком на 9600 8N1 по RS-485, а с модемом на 9600 8N1 по второму UART.

Прошивка ESP32 для варианта A по сути повторяет уже готовый скетч esp32-meter-mqtt-Ci-2: вместо WiFi + MQTT — цикл «Modbus-запрос → ответ → AT+SEND». Ответ счётчика отправляется целиком, вместе с CRC, чтобы декодер мог его проверить.

AT-команды модема (реальный набор EWD95M)

Модем отвечает на 9600 8N1. Синтаксис: AT+CMD=? читает значение, AT+CMD=value записывает, AT+CMD? печатает подсказку, AT? выводит весь список. Ответ OK или AT_ERROR. Символы +++ не нужны, модем всегда в командном режиме.

Отправка данных после присоединения: AT+SEND=2:1:0:0103040001E240E2A3 — порт 2, одна попытка, без подтверждения, payload в hex. Проверка канала: AT+LINKC добавит Link Check к следующему uplink, ответ покажет запас по сигналу и число услышавших шлюзов.

Порядок, чтобы не ловить «Join failed» Сначала завести устройство на сервере (DevEUI, JoinEUI, AppKey, RU864), убедиться, что БС-1.2 онлайн, и только потом давать AT+CJOIN. Модем при неудаче повторяет Join с ростом SF, каждая попытка занимает эфир на секунды.

Настройка сервера и шлюза

Вега БС-1.2. В веб-интерфейсе станции: частотный план RU868 (864.1–870 МГц, каналы по умолчанию 868.9 и 869.1 для Join), режим подключения к серверу — Semtech UDP packet forwarder (порт 1700) для ChirpStack или родной протокол Веги для IOT Vega Server. Убедись, что станция синхронизирована по времени: без NTP/GPS RX-окна для Join Accept уезжают, и устройство не присоединяется.

ChirpStack v4.

  1. Gateways → добавить БС по Gateway ID (EUI станции), регион RU864.
  2. Device profiles → создать: Region RU864, MAC 1.0.3, Regional params A, Class A, «Supports OTAA» включено. В этот же профиль вставляется декодер из шага 3 (Codec: JavaScript functions).
  3. Applications → создать приложение → Add device: DevEUI, JoinEUI, профиль. На вкладке OTAA keys — AppKey (в v4 поле называется «Application key», для 1.0.x это тот же NwkKey).
  4. Вкладка Events: жди join, затем up с полем object — это результат декодера.

IOT Vega Server. Устройства → Добавить → DevEUI, AppEUI, AppKey, OTAA, класс A. Сырой payload приходит в HEX в карточке устройства и в WebSocket/MQTT-интеграции; JavaScript-декодер сервер Веги не исполняет, поэтому тот же скрипт из шага 3 запускается снаружи — в Node-RED или в Python-мосте (см. последний раздел).

ШАГ 3Декодер payload на сервере

Декодер не полагается на позицию байтов: он сканирует пакет, находит Modbus-кадр по адресу, функции, длине и совпадению CRC16, и только потом разбирает данные. Так он переживает и служебные байты Ebyte в начале пакета, и мусор в конце. Формат числа выбирается в CONFIG после того, как ты подтвердил его сканом из шага 1.

// ChirpStack v4 (Device profile → Codec → JavaScript functions)
// Также совместим с TTN v3: та же функция decodeUplink.

var CONFIG = {
  slave: 1,            // адрес счётчика в Modbus
  format: "u32",       // "u32" = целое ×scale, "f32" = float32 big-endian, "f32sw" = float32 со свопом слов
  scale: 0.01,         // множитель для u32 (0.01 → сотые кВт·ч)
  extra: {             // необязательно: другие регистры, если опрашиваешь блоком
    // "voltage_v":  { offset: 16, type: "u16", scale: 0.1 }
  }
};

function crc16(bytes, start, end) {
  var crc = 0xFFFF;
  for (var i = start; i < end; i++) {
    crc ^= bytes[i];
    for (var b = 0; b < 8; b++) crc = (crc & 1) ? ((crc >>> 1) ^ 0xA001) : (crc >>> 1);
  }
  return crc & 0xFFFF;
}

// Ищет валидный кадр ответа Modbus (функция 03/04) в произвольном массиве байт
function findModbusFrame(bytes, slave) {
  for (var i = 0; i + 5 <= bytes.length; i++) {
    if (bytes[i] !== slave) continue;
    var fn = bytes[i + 1];
    if (fn !== 0x03 && fn !== 0x04) continue;
    var n = bytes[i + 2];
    var end = i + 3 + n + 2;
    if (end > bytes.length) continue;
    var crc = crc16(bytes, i, end - 2);
    var got = bytes[end - 2] | (bytes[end - 1] << 8);   // CRC в кадре: младший байт первым
    if (crc === got) return { start: i, fn: fn, data: bytes.slice(i + 3, i + 3 + n) };
  }
  return null;
}

function readNumber(data, offset, type) {
  var dv = new DataView(new Uint8Array(data).buffer);
  switch (type) {
    case "u16":   return dv.getUint16(offset, false);
    case "s16":   return dv.getInt16(offset, false);
    case "u32":   return dv.getUint32(offset, false);
    case "s32":   return dv.getInt32(offset, false);
    case "f32":   return dv.getFloat32(offset, false);
    case "f32sw": {                                  // словa переставлены: [hi16][lo16] → [lo16][hi16]
      var sw = [data[offset+2], data[offset+3], data[offset], data[offset+1]];
      return new DataView(new Uint8Array(sw).buffer).getFloat32(0, false);
    }
  }
  return null;
}

function decodeUplink(input) {
  var bytes = input.bytes;
  var frame = findModbusFrame(bytes, CONFIG.slave);
  if (!frame) {
    return { data: { error: "modbus frame not found", raw: toHex(bytes) }, warnings: ["no valid CRC"] };
  }
  if (frame.data.length < 4) {
    return { data: { error: "short response", raw: toHex(bytes) } };
  }
  var energy;
  if (CONFIG.format === "u32") energy = readNumber(frame.data, 0, "u32") * CONFIG.scale;
  else energy = readNumber(frame.data, 0, CONFIG.format);

  var out = {
    energy_kwh: Math.round(energy * 100) / 100,
    fport: input.fPort,
    modbus_fn: frame.fn,
    raw: toHex(bytes)
  };
  for (var key in CONFIG.extra) {
    var e = CONFIG.extra[key];
    if (e.offset + 2 <= frame.data.length) {
      var v = readNumber(frame.data, e.offset, e.type);
      if (v !== null) out[key] = Math.round(v * (e.scale || 1) * 1000) / 1000;
    }
  }
  return { data: out };
}

function toHex(bytes) {
  var s = "";
  for (var i = 0; i < bytes.length; i++) s += ("0" + bytes[i].toString(16)).slice(-2);
  return s;
}

// Совместимость с ChirpStack v3
function Decode(fPort, bytes) { return decodeUplink({ bytes: bytes, fPort: fPort }).data; }

Мост в OpenTwins

Ditto-маппер на 192.168.0.199 принимает сообщения вида {"device_id":"namespace:name","data":{...}} в топик opentwins/namespace:name. Короткий мост на Python берёт uplink из MQTT ChirpStack (топик application/+/device/+/event/up), уже с полем object от декодера, и перекладывает его в формат OpenTwins:

import json, paho.mqtt.client as mqtt

CS = ("192.168.0.199", 1883)        # MQTT ChirpStack
OT = ("192.168.0.199", 30511)       # MQTT OpenTwins
THING = "lower_lab:ddsd6868"        # twin в Ditto

out = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2); out.connect(*OT); out.loop_start()

def on_up(c, u, m):
    ev = json.loads(m.payload); obj = ev.get("object") or {}
    if "energy_kwh" not in obj: return
    data = {"active_energy_positive_kwh": obj["energy_kwh"]}
    for k in ("voltage_v", "current_a", "active_power_w", "frequency_hz"):
        if k in obj: data[k] = obj[k]
    out.publish(f"opentwins/{THING}", json.dumps({"device_id": THING, "data": data}))

inp = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2); inp.on_message = on_up
inp.connect(*CS); inp.subscribe("application/+/device/+/event/up"); inp.loop_forever()

Для IOT Vega Server тот же мост подписывается на его MQTT/WebSocket, получает HEX и вызывает Python-версию декодера (логика та же: найти кадр по CRC, разобрать uint32/float32). Twin lower_lab:ddsd6868 нужно один раз создать в OpenTwins, как созданы oven и compressor.
